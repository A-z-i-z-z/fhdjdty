**Findings:**

- **minor** `app/src/main/java/dev/pocketagent/app/data/Transcript.kt`:136: splitLong does not always rebuild the original text after Hermes joins the parts with a newline. When it cuts at a space (no newline in the second half of the window), that space comes back as a newline. When there is neither, the hard cut at max characters splits a word, token or base64 run, and Hermes inserts a newline there. Example: a user pastes a 70,000-character log or minified JSON line. The model gets it with a newline inserted inside a token, so the content differs from what was typed (both for user/assistant text in HermesApi and for an over-long system prompt). Only texts over 60,000 characters are affected; shorter texts are unchanged. **Fix:** Cut only at a newline, which is dropped and restored exactly by the join. If the window has no newline, keep the text unsplit (Hermes then truncates it as before) or cut at the space and keep the space at the end of the left part, so a join reads 'word \nword', and say so in the KDoc. Never cut inside a run with neither newline nor space. Add a test that joins the parts with '\n' and compares the result with the input for the newline-cut case.

**Findings:**

- **major** `tools/phone-lib.ps1`:804: The robot never checks which window has focus before injecting input. Send-PaTap (804), Send-PaKey (806-811), Send-PaText (813-825), the swipe op (1138-1151), cached taps (913-920, used by every owner perf scenario), the 'clear' keystrokes (952-953: keyevent 123 plus 60 DEL), a type without a selector (948-955) and the notification reply (1297-1299) all go straight to 'adb shell input'. Only a dump-based tap is partly protected, because the node must carry the package at dump time, and there is still a gap between dump and tap. Concrete sequence on the owner: phone-perf -Owner, P1 taps tab.home (cached), then runs 'swipe up/down' 30 times over 3 repeats with no dump. If the new build crashes or One UI shows a dialog, those swipes (and P5's ~45 cached taps plus BACK keys) land in the launcher or whatever app is in front. This is the incident AGENTS.md records. **Fix:** Add Assert-PaForeground: run 'dumpsys window' and parse mCurrentFocus / mFocusedApp (fall back to 'dumpsys activity activities' and look for topResumedActivity). Throw 'refused: focus is <component>, not <Pa.Package>' unless the focused window's package equals $script:Pa.Package. Allow com.android.systemui only inside the notification op while the shade is expanded. Call it as the first statement of Send-PaTap, Send-PaKey, Send-PaText, the input swipe in Invoke-PaOpSwipe and the hold-tap in Invoke-PaOpTap, and before the clear keystrokes. Treat its failure as fatal for the whole run: rethrow past the scenario loop, so that the finally blocks still restore scales and practice but no further input is sent. For cached taps, check before every tap; it is a cheap dumpsys call, not a uiautomator dump.
- **major** `tools/phone-lib.ps1`:1450: The free-form 'adb' op is guarded only by Assert-PaTwinTarget, which checks the session's target package, and by a deny list of whole words. Its arguments can name any package, and the deny list is easy to get around. Examples: ['install-multiple','-r','-d','app\build\outputs\apk\debug\app-debug.apk'] (when the last local build was -OwnerDebug) downgrade-installs over dev.pocketagent.app without Assert-OwnerInstallAllowed. ['shell','pm${IFS}clear dev.pocketagent.app'] splits into the words 'pm${IFS}clear' and 'dev.pocketagent.app', passes the deny regex, and the device shell expands it to 'pm clear dev.pocketagent.app', wiping all of the owner's data. ['shell','pm','disable-user','dev.pocketagent.app'] and ['shell','cmd','appops','set','dev.pocketagent.app',...] pass unchanged. No scenario uses the op today, so this is a guard that does not hold, not a risk tonight. **Fix:** Replace the deny list with an allow list. The first argument must be one of shell, pull, logcat or devices; never install*, uninstall, push or reverse. For shell, the joined command must match a fixed set of read-only verbs (dumpsys, getprop, cmd statusbar, am broadcast/start with -n built from $PaTwinPackage). Refuse any argument that contains $PaOwnerPackage as a whole token (regex '(^|[^.\w])dev\.pocketagent\.app($|[^.\w])') or any of $ ` ; | & > < ( ) \ characters. Add the bypass strings above to the self test.
- **major** `tools/phone-lib.ps1`:1417: Invoke-PaOpInstall runs 'adb install -r <apk>' on any file the scenario names. Assert-PaTwinTarget only proves the session targets the twin; it says nothing about the APK. The twin and owner-debug builds share the output path app\build\outputs\apk\debug\app-debug.apk, so a twin scenario with {op:install, apk:'app/build/outputs/apk/debug/app-debug.apk'} run after a 'local-build -OwnerDebug' installs an owner-package APK over the owner's app. That skips the certificate, backup and Linux-image checks, and an APK built from other parts re-extracts the image. **Fix:** Before installing, read the APK's package with aapt2 ('dump packagename', build-tools 36.0.0 as in local-build) and throw 'refused: install: the APK is for <pkg>, not the twin' unless it equals $PaTwinPackage. If aapt2 is missing or fails, refuse (do not install).
- **minor** `tools/local-build.ps1`:738: unverified: the twin build and the owner-debug build use the same Gradle variant ('debug') and the same build directory, and local-build never cleans between them. BuildConfig.IS_TWIN, APP_VARIANT and DEEP_LINK_SCHEME are compile-time constants, which Kotlin inlines into its callers (for example DebugLinks.parseParts' default isTwin, runSeed, the variant line in PocketApp). If incremental Kotlin compilation does not recompile those callers when the Java BuildConfig changes, an -OwnerDebug build made right after a twin build could carry IS_TWIN=true behaviour. That would let the debug link seed test data into the owner's chats. Show-ApkFacts checks only the package, debuggable and target SDK, so it would not notice. **Fix:** In Invoke-Build, write the identity to dist\last-build-identity.txt. When it differs from this run's identity (or the file is missing), add '--rerun-tasks' for :app:compileDebugKotlin, or run ':app:clean' first. After the build, check the identity against app.log's 'variant=' line on first start, or read BuildConfig from the dex with dexdump, and stop on a mismatch.
